# 坡度算法仿真结论

针对 Edge 840 (1Hz, 无轮速, GNSS speed + 气压计) 场景的坡度算法选型仿真。
`final_compare.py` 为最终可复现版本（seed=1234），`sim_grade.py` 为探索过程。

## 场景建模
- 1Hz 更新；GPS 速度带 σ=0.3m/s 噪声 + 1s 延迟；气压海拔 σ=0.4m 噪声
- 剖面：平路→(20m过渡)→6%→-8%→3%→0%
- 距离源：GNSS speed（不用位置差分，防横向漂移卷入坡度）
- 海拔源：气压计（Baro）

## 最终对比（KPI: 入坡爬到真值90%延迟 / 稳定段噪声σ / 稳态偏差 / 峰值过冲）

| 算法 | 延迟 | 稳定噪声σ | 稳态偏差 | 过冲 |
|--------|:---:|:---:|:---:|:---:|
| α-β(现状,View.mc手写) | 2s | 1.54% | -0.16% | 4.00% |
| **KF-vz 轻降噪(r_h=0.16,q_vz=0.02)** | **2s** | **1.00%** | 0.14% | **2.55%** |
| KF-vz 平衡(0.16,0.05) | 2s | 1.36% | 0.12% | 3.59% |
| KF-vz 响应快(0.08,0.04) | 2s | 1.58% | 0.11% | 4.09% |
| 3s窗口差分 | 0s | 40%+ | — | — |

## 决定性的三个判断（仿真验证，非猜测）

1. **短窗口差分(3s)直接淘汰**：σ≈40% 灾难。验证"不能直接对气压海拔做差分"——短距离(3s≈24m)上 σh=0.4m 经差分放大到坡度噪声几十%。
2. **正确建模是 KF-vz，不是 4态+坡度硬约束**：把坡度直接当量测(4态, g_obs=2s窗口)会捡回窗口噪声(σ~40%)。正确做法：状态只有 `[h, vz]`，海拔观测驱动 vz 累积(逐步平滑)，**坡度 = vz/v 输出**。这本质是 α-β 的框架化，但 Q/R 可精调后噪声 -35%、过冲 -36%。
3. **坡度硬约束(g·v 锁定, 用户第5点)不可取**：会钉死坡度(仿真最初 Kalman 卡在 ~0 不动)。应"vz 由海拔观测驱动, 坡度=vz/v 导出"。

## 结论
**KF-vz(轻降噪 r_h=0.16,q_vz=0.02) 取代手写 α-β**：同 2s 延迟下噪声 1.54%→1.00%、过冲 4%→2.55%。已落地到 View.mc。Monkey C 里 2 状态卡尔曼计算量可忽略。

## 关键设计原则（用户提供的算法分析，仿真验证后采纳）
- 坡度 = 垂直速度 / 水平速度 (vz/v)，水平速度用 GNSS speed（滤波后），不用位置差分
- 垂直速度由高度状态估计，不能直接差分（会放大噪声）
- 速度需轻量滤波(时间常数0.5~1.5s)，防急加速时 GNSS 响应滞后导致坡度错误
- 道路坡度变化率天然受限 → 给坡度状态小过程噪声，Kalman 借此降延迟又压噪
- 高可信时才快速更新（GNSS好+速度高+Baro稳），低速/信号差时降级，避免无意义抖动
